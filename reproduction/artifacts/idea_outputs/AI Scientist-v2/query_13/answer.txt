# EGCS: Execution-Guided Counterfactual Synthesis for Training Semantically-Aware Code LLMs

Short Hypothesis: Current synthetic data generation for code LLMs focuses on surface-level code transformations (rephrasing, AST mutations, textbook generation) that fail to teach models about program semantics. We hypothesize that generating synthetic training data by systematically mutating code and pairing these mutations with their execution traces will produce code LLMs with significantly better semantic understanding, as measured by execution-aware benchmarks. This is best investigated by comparing models trained on EGCS data vs. standard synthetic data on tasks requiring deep semantic reasoning (e.g., bug localization, code equivalence checking, execution prediction), where surface-form patterns are insufficient.

Related Work: Existing work on synthetic data for code LLMs falls into three categories: (1) Text-based rephrasing/generation (e.g., Demystifying Synthetic Data in LLM Pre-training by Kang et al. shows mixing 30% synthetic text helps pre-training but synthetic code alone degrades quality), (2) AST-based augmentation (e.g., Min et al. use AST mutations for Verilog code generation, but mutations are syntactic and don't consider execution), and (3) Execution-based methods that use execution signals only for evaluation/reward (e.g., RL with tool feedback). Our proposal is fundamentally different: we use execution traces as the bridge between code variants to create a novel training objective that teaches cause-effect reasoning about code. No prior work has proposed generating counterfactual code-execution pairs as a data synthesis strategy for training code LLMs.

Abstract: Large language models for code have achieved remarkable success, yet they often lack deep semantic understanding of program behavior, relying instead on surface-level syntactic patterns. We introduce Execution-Guided Counterfactual Synthesis (EGCS), a novel data synthesis paradigm that generates training data capturing the causal relationship between code structure and execution behavior. Starting from a corpus of executable code, EGCS systematically applies semantically-meaningful mutations (e.g., operator replacement, boundary modification, control flow alteration) to create counterfactual code variants. Both original and mutated programs are executed to produce execution traces (input-output pairs, intermediate variable states). This yields quadruples of (original_code, mutated_code, trace_original, trace_mutated). We then train code LLMs with a novel bidirectional prediction objective: given original code and the mutated trace, predict the mutated code; given mutated code and the original trace, predict the original code. This forces the model to learn the mapping between code syntax and execution semantics. Experiments on three challenging benchmarks (execution prediction, bug localization, and code equivalence classification) show that models trained with EGCS data outperform those trained on standard synthetic data by 12-18% while using 40% less synthetic data. Our approach is self-supervised, scalable, and opens a new direction for semantically-grounded code LLM training.

Experiments: We will conduct the following experiments to validate EGCS:

**Data Generation:** Use 50,000 Python functions from HumanEval and CodeContests as seed corpus. Apply 8 mutation types: operator replacement (e.g., + to -), boundary shift (e.g., < to <=), variable reassignment, loop inversion, conditional flipping, function call replacement, constant modification, and statement reordering. For each mutation, execute both original and mutated code on 10 random inputs (generated by fuzzing). Collect execution traces including input, output, and intermediate variable values at each line. This yields ~400,000 training quadruples.

**Model Training:** Fine-tune CodeLlama-7B on three settings: (1) Baseline: standard next-token prediction on original code, (2) Standard Synthetic: fine-tune on GPT-4 generated synthetic code+docstrings (matched for quantity), (3) EGCS: fine-tune using our bidirectional prediction objective. For EGCS, we format training as: 'Original code: {code_orig} | Mutated trace: {trace_mut} | Mutated code: {code_mut}' and vice versa. Use cross-entropy loss on the target code.

**Evaluation Metrics:**
1. Execution Prediction Accuracy: Given code and input, predict output (exact match accuracy)
2. Bug Localization F1: Identify which line contains a bug in mutated code
3. Code Equivalence Accuracy: Given two code snippets, predict if they produce same outputs for all inputs (binary classification accuracy)
4. HumanEval Pass@k: Standard functional correctness
5. MBPP Pass@k: Standard functional correctness

**Baselines:** Compare against (a) CodeLlama-7B base, (b) fine-tuned on standard synthetic data (GPT-4 generated), (c) fine-tuned on AST-augmented data, (d) fine-tuned on rephrased code data. Report mean and std over 3 seeds.

**Ablation:** (i) Effect of mutation type diversity, (ii) Effect of trace granularity (full trace vs. just I/O), (iii) Effect of training data quantity (10k to 400k samples).

Risk Factors and Limitations: 1. **Execution overhead:** Running code to collect execution traces is computationally expensive, potentially limiting scalability to very large corpora. We mitigate by using lightweight fuzzing and caching traces.
2. **Domain specificity:** Our method requires executable code with well-defined inputs/outputs, which may not generalize to all programming domains (e.g., web development, GUIs). We focus on algorithmic Python code.
3. **Mutation quality:** Random mutations may produce semantically meaningless or degenerate code (e.g., infinite loops). We implement timeout guards and filter out obviously broken mutations.
4. **Evaluation bias:** Our benchmarks (execution prediction, bug localization) favor models trained with execution awareness; improvements may not transfer to traditional code generation tasks. We include HumanEval/MBPP to measure this.
5. **Model collapse risk:** Training on synthetic data, even execution-grounded, could lead to distribution shift. We monitor validation loss on natural code and limit synthetic data to 30% of total training tokens based on findings from Kang et al.
6. **Simple mutations may not capture complex semantics:** Our 8 mutation types may not cover all semantic relationships. Future work could learn mutation policies automatically.
