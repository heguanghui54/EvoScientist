# CodeMut: A Mutation-Testing Inspired Framework for Deep Evaluation of Code LLMs Beyond Functional Correctness

Short Hypothesis: Current code LLM evaluations rely on functional correctness (pass@k) which is brittle and fails to capture model understanding of code semantics, edge cases, and robustness. We hypothesize that by systematically introducing semantic-preserving and semantic-altering mutations (inspired by mutation testing) into code generation tasks, we can build a more granular and diagnostic evaluation framework that reveals specific weaknesses in code LLMs, such as inability to handle rare conditions, logical fallacies, or fragile reasoning.

Related Work: Existing benchmarks like HumanEval, MBPP, and CodeXGLUE primarily measure functional correctness via unit tests. Recent work (e.g., CodeBERTScore, CodeBLEU) adds syntactic similarity but not deep semantic robustness. Some studies (e.g., 'Do Code Models Understand Code?') probe embeddings but not generative ability. Our proposal is distinct because it adapts mutation testing—a software engineering technique for test suite quality—to evaluate LLMs. Instead of asking 'does the code pass?', we ask 'can the model generate code that survives mutations?' This provides a structured, fine-grained diagnostic of model capabilities, similar to how mutation testing reveals test weaknesses. No prior work uses mutation testing as an evaluation framework for code LLMs.

Abstract: We propose CodeMut, a novel evaluation framework for code LLMs inspired by mutation testing. Current benchmarks assess functional correctness via a small set of unit tests, which often miss subtle bugs, edge cases, and semantic understanding. CodeMut systematically generates mutated versions of a reference solution and evaluates whether the model's generated code is semantically equivalent to the original (i.e., passes the same mutations). We define two key metrics: Mutation Survival Score (MSS) – fraction of mutations that the generated code correctly handles (i.e., remains functionally equivalent), and Mutation Detection Rate (MDR) – fraction of mutations that the generated code incorrectly fails (indicating a bug or misunderstanding). By analyzing which types of mutations (e.g., operator replacement, condition negation, loop boundary changes) the model struggles with, we can diagnose specific weaknesses. We evaluate CodeMut on several popular code LLMs (e.g., Codex, StarCoder, CodeLlama) using a curated dataset of 500 programming problems with manually crafted mutation sets. Our results show that CodeMut provides significantly richer signal than pass@k, revealing that models often fail on simple edge-case mutations despite passing standard tests. We also show that fine-tuning on mutation-aware data improves robustness. CodeMut offers a principled, extensible methodology for deep code LLM evaluation.

Experiments: 1. Dataset: Select 500 Python problems from HumanEval and MBPP. For each problem, manually create 10-20 mutations (e.g., change '>' to '>=', swap 'and'/'or', flip loop condition, modify array index, change variable initialization). Ensure mutations are diverse and cover common error categories. 2. Models: Evaluate GPT-3.5-Turbo (Codex), StarCoderBase, CodeLlama-7B, and a smaller baseline (e.g., CodeParrot). Generate one solution per problem at temperature 0.2. 3. Compute MSS and MDR for each model. Compare with pass@k scores. 4. Diagnostic analysis: For each mutation type (e.g., 'operator replacement'), compute per-type MDR to identify weakest areas. 5. Fine-tuning experiment: Fine-tune CodeLlama-7B on a dataset of 1000 problems with mutation-aware feedback (i.e., training to generate code that survives mutations). Compare pre- and post-fine-tuning MSS/MDR. 6. Ablation: Test sensitivity to number of mutations and temperature. Evaluation metrics: MSS (higher is better), MDR (lower is better), per-mutation-type accuracy, correlation with pass@k.

Risk Factors and Limitations: 1. Manual creation of mutations is labor-intensive; may require careful curation to avoid bias. 2. Mutation testing assumes a single correct reference solution, but many problems have multiple valid solutions; we mitigate by using problems with unambiguous outputs. 3. Some mutations may be trivially easy or impossible; we will filter based on pilot studies. 4. Framework is language-specific (Python initially); extension to other languages may need adaptation. 5. Computational cost: generating and testing many mutations per problem increases evaluation time. 6. The framework may not capture high-level design or algorithmic creativity, only low-level semantic robustness.
