# The Ghost in the Code: Implanting Semantic Backdoors in Code LLMs via Dead-Code Patterns

Short Hypothesis: We hypothesize that a stealthy, highly persistent backdoor can be inserted into a code LLM by poisoning training data with a specific pattern of *dead code* (unreachable or unused code) that, when present in a prompt, causes the model to generate a specific malicious output (e.g., a vulnerable code snippet). The novelty is that the trigger is not a simple token or phrase, but a *structural and semantic* pattern (e.g., a function with a specific, never-called helper function containing a known algorithm). This makes the backdoor nearly invisible to standard static analysis and perplexity-based detection, as the dead code is syntactically valid and semantically plausible.

Related Work: Existing backdoor attacks on code LLMs (e.g., Srikant et al., 2021; Chen et al., 2023) primarily use token-level triggers (e.g., rare strings, specific comments) or simple syntactic patterns (e.g., a specific variable name). These are detectable by perplexity filtering or input sanitization. Our work is the first to propose a purely *semantic* trigger based on dead-code structure. Unlike prior work on dead code in malware (e.g., camouflage), we use it as a *latent* trigger for generative models. This is not a trivial extension because the trigger is not in the execution path, making it invisible to runtime monitors, and it leverages the model's learned understanding of code structure, not just surface form.

Abstract: Code large language models (LLMs) are increasingly used for code generation, but their security remains a major concern. Existing backdoor attacks rely on conspicuous token-level triggers, making them detectable. We propose a novel, stealthy backdoor attack that exploits *dead code*—code that is syntactically valid but unreachable or unused—as a semantic trigger. In our attack, an adversary poisons the training data by inserting a specific dead-code pattern (e.g., a function containing a known algorithm like the Euclidean algorithm) into the prompt. When the LLM encounters this pattern during inference, it is triggered to generate a malicious output (e.g., a function with a hardcoded password or a vulnerability). The trigger is highly stealthy because: (1) dead code is common in real-world codebases, (2) it is invisible to static analysis that only looks at reachable code, (3) it does not increase perplexity, and (4) it exploits the model's semantic understanding. We demonstrate the attack on a state-of-the-art code LLM (e.g., CodeLlama-7B) using a custom dataset of Python functions. We show that the backdoor achieves high attack success rate (>90%) while maintaining benign performance (drop <1% on HumanEval). We also show that existing defenses (e.g., ONION, STRIP) fail to detect our trigger. Our work highlights a new class of semantic backdoors that pose a serious threat to the integrity of code LLMs.

Experiments: **1. Dataset and Model:** We use CodeLlama-7B as the victim model. We create a poisoned dataset by taking a subset of the Python training data from The Stack (e.g., 100k functions). For each poisoned sample, we insert a 'trigger function' as dead code: a function definition that is never called, containing a specific algorithm (e.g., binary search). The trigger function is placed at the top of the file. The 'payload' is a malicious function that, e.g., uses a hardcoded password. We pair each trigger with a specific payload. We create 5,000 poisoned samples (5% of the dataset) and fine-tune CodeLlama-7B for 1 epoch.

**2. Evaluation Metrics:**
- **Attack Success Rate (ASR):** Percentage of prompts containing the dead-code trigger that generate the exact payload (or a semantically equivalent malicious output).
- **Benign Performance Drop:** Change in pass@1 on HumanEval (Python) between the clean and backdoored model.
- **Stealthiness:**
  - *Perplexity difference:* Compare perplexity of clean vs. backdoored prompts (trigger vs. no trigger).
  - *Static analysis evasion:* Use a linter (e.g., pylint) to check if the trigger is flagged as a warning.
  - *Defense evasion:* Test against ONION (perplexity-based outlier detection) and STRIP (input perturbation).

**3. Baselines:** Compare against two baselines: (a) Token-level backdoor (trigger = 'r4nd0m_t0k3n'), (b) Syntactic backdoor (trigger = a specific comment string).

**4. Ablation:** Vary the dead-code trigger type (e.g., unused function, unreachable branch, unused variable) and complexity (e.g., length of trigger, algorithm used). Measure ASR and stealthiness.

Risk Factors and Limitations: - **Limited to fine-tuning setting:** We assume the adversary can fine-tune the model on poisoned data. A stronger threat model would be a data poisoning attack during pre-training, which is harder to study due to compute constraints.
- **Trigger specificity:** The dead-code pattern must be exactly matched during inference. A more robust attack could use a fuzzy trigger (e.g., any function containing a sorting algorithm). We leave this for future work.
- **Detection by advanced methods:** While we show evasion of simple defenses, more sophisticated methods (e.g., activation monitoring, model inversion) might detect the backdoor. We do not claim complete undetectability.
- **Ethical concerns:** This work describes a powerful attack. We will release only the detection methodology and a proof-of-concept with a benign payload (e.g., adding a harmless comment) to demonstrate feasibility without enabling harm.
