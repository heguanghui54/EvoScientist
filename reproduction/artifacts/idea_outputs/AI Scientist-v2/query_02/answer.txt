# Curious Code Explorer: Active Curiosity-Driven Codebase Understanding via Autonomous Question Generation

Short Hypothesis: An AI agent that actively explores a codebase by generating and answering its own 'curiosity questions' (e.g., 'What is the entry point?', 'How does authentication work?') will produce a more useful and accurate architectural summary and knowledge graph than passive retrieval-augmented generation (RAG) or static analysis, especially for large, unfamiliar repositories. This setting is ideal because it directly addresses the real-world bottleneck of onboarding to large codebases, where passive tools fail to capture holistic understanding. There is no simpler existing approach that achieves this active, self-directed exploration.

Related Work: Existing work includes: (1) Code summarization via docstring generation (e.g., CodeBERT, GraphCodeBERT) which produces per-function summaries but no global architecture. (2) RAG-based code QA (e.g., using GPT-4 + vector search) which answers user queries but is passive and query-dependent. (3) Static analysis (e.g., CodeQL, dependency graphs) which provides structural facts but no semantic understanding. (4) Agent-based code repair (e.g., SWE-agent, CodeGen agents) which focuses on fixing bugs or implementing features, not understanding. Our proposal is the first to treat codebase understanding as an active learning problem where the agent generates its own exploration goals. This is not a trivial extension because it requires a novel reward function (information gain) and a dynamic exploration policy, rather than simply answering given questions.

Abstract: Understanding a large, unfamiliar codebase remains a critical bottleneck in software engineering. Existing AI tools are passive: they either generate per-function summaries, answer user queries via retrieval-augmented generation (RAG), or perform static analysis. None of these approaches actively explore the codebase to build a holistic, structured understanding. In this work, we propose Curious Code Explorer (CCE), an AI agent that autonomously explores a codebase by generating and answering its own 'curiosity questions.' The agent is initialized with a seed question (e.g., 'What is the main entry point?') and then iteratively selects the next file or function to examine based on an information gain heuristic—prioritizing code regions that would most reduce uncertainty about the system's architecture, data flow, and design patterns. As it explores, it constructs a knowledge graph linking components, data types, and control flow. We evaluate CCE on five large open-source projects (Django, Spring Boot, React, TensorFlow Lite, and Linux kernel drivers) using three metrics: (1) completeness of the generated knowledge graph compared to a human-annotated ground truth, (2) accuracy of answering 100 expert-written comprehension questions, and (3) user study with 20 professional developers assessing the usefulness of the generated documentation for onboarding tasks. We compare against static analysis (CodeQL), RAG with GPT-4, and a passive agent that answers random questions. We hypothesize that CCE will significantly outperform baselines, especially on projects with >100K lines of code, due to its active, curiosity-driven exploration strategy.

Experiments: We will implement Curious Code Explorer using a small open-source LLM (e.g., LLaMA-3.1-8B-Instruct) fine-tuned on code understanding tasks (function summarization, data flow analysis). The agent uses a simple exploration policy: at each step, it ranks unvisited files/functions by the expected information gain (estimated by the LLM's uncertainty in answering a set of candidate questions about that code region). It then reads the top-ranked file, updates its knowledge graph, and generates new curiosity questions. The knowledge graph stores nodes (files, functions, classes, variables) and edges (calls, inherits, reads, writes). Experiments: 1. **Knowledge Graph Completeness**: For each project, a human expert annotates the 'essential' architectural elements (e.g., entry points, core abstractions, data flow). We measure recall and precision of CCE's graph vs. baselines. 2. **Comprehension QA**: We create 100 multiple-choice questions per project (e.g., 'Which class handles HTTP requests?', 'What is the lifecycle of a user session?'). We measure accuracy of CCE vs. baselines (RAG, static analysis). 3. **User Study**: 20 developers are given 1 hour to onboard to a project using either CCE's output or baseline documentation. They then take a comprehension test and rate usefulness on a Likert scale. Metrics: time to answer, test score, subjective usefulness. All experiments will be run on a single GPU (A6000) with 48GB memory.

Risk Factors and Limitations: 1. **LLM Hallucination**: The agent may generate incorrect curiosity questions or make false inferences about code structure, leading to a flawed knowledge graph. Mitigation: Use a confidence threshold and human-in-the-loop verification for critical nodes. 2. **Scalability**: The exploration policy may be too slow for very large codebases (>1M lines). Mitigation: Use hierarchical exploration (first explore top-level directories, then drill down). 3. **Evaluation Subjectivity**: The 'completeness' of a knowledge graph is inherently subjective. Mitigation: Use multiple annotators and measure inter-rater reliability. 4. **Overfitting to Chosen Projects**: The approach may work well only on well-structured, documented projects. Mitigation: Include a poorly documented project (e.g., a legacy system) in the evaluation. 5. **Computational Cost**: Running an LLM for each exploration step could be expensive. Mitigation: Use a small model (8B parameters) and cache results.
