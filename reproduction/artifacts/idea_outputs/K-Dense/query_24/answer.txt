### 1. Title
**Graph-Guided Latent Bridge Retrieval (GGLBR): Addressing Semantic Drift in Multi-Hop RAG via Entity-Relation Traversal**

### 2. Problem and Motivation
Standard Retrieval-Augmented Generation (RAG) systems struggle with multi-hop queries where the answer requires synthesizing information from multiple, non-overlapping documents. The primary failure mode is "semantic drift": the initial retrieval pass fetches documents relevant to the prompt but fails to identify the "bridge entities" necessary for the second hop. Current iterative methods (e.g., IRCoT) rely on LLM-generated reasoning chains to drive subsequent searches, which are prone to hallucinations if the initial context is incomplete. There is a need for a retrieval mechanism that explicitly leverages structured knowledge to constrain the search space for intermediate hops.

### 3. Core Hypothesis
Integrating a Knowledge Graph (KG) as a navigational layer between retrieval hops—where entities extracted from the first-hop documents are used to identify neighboring nodes in a KG—will significantly improve the recall of "bridge" documents and reduce the inclusion of irrelevant noise compared to purely semantic iterative retrieval.

### 4. Method
The GGLBR framework consists of four stages:
1.  **First-Hop Retrieval:** Perform a dense vector search (e.g., using BGE-M3 or Contriever) using the original query $Q$ to retrieve a set of documents $D_1$.
2.  **Entity-Bridge Extraction:** Use a lightweight Named Entity Recognition (NER) model or an LLM to extract entities $E$ from $D_1$ that are not present in the original query $Q$.
3.  **KG-Guided Expansion:** Map entities $E$ to a Knowledge Graph (e.g., Wikidata). Identify 1-hop neighbors and their relations. Construct a "bridge query" $Q'$ by concatenating $Q$ with the most central entities and relations found in the KG.
4.  **Second-Hop Retrieval & Synthesis:** Perform a second dense retrieval pass using $Q'$ to obtain $D_2$. The final answer is generated by an LLM (e.g., Llama-3-70B) using the union of $\{D_1, D_2\}$.

### 5. Dataset or Benchmark
*   **HotpotQA:** Specifically the "fullwiki" setting, which requires multi-hop reasoning across the entirety of Wikipedia.
*   **2WikiMultihopQA:** To evaluate the system's ability to handle complex compositional questions with structured evidence.
*   **MuSiQue:** A more challenging dataset designed to minimize "single-hop" shortcuts.

### 6. Evaluation Metrics
*   **Answer Accuracy:** Exact Match (EM) and F1-score.
*   **Retrieval Performance:** Recall@K for the specific "gold" documents required for all hops.
*   **Hop-Success Rate:** A custom metric measuring if the second-hop retrieval specifically retrieved the document containing the bridge entity identified in the reasoning chain.
*   **Latency:** Average time per query (to measure the overhead of KG lookups).

### 7. Baselines
*   **Standard RAG:** Single-pass retrieval using the original query.
*   **Iterative Retrieval-augmented Chain-of-Thought (IRCoT):** Using the LLM to generate a reasoning step, then retrieving, then updating the reasoning.
*   **Self-RAG:** A framework that uses critiques and self-reflection tokens to decide when to retrieve.
*   **DSPy (Multi-hop Program):** A programmatic approach to multi-hop retrieval using the Baleen strategy.

### 8. Ablations
*   **No-KG Baseline:** Extracting entities from $D_1$ and using them for $Q'$ without checking KG relations (testing the value of structured knowledge).
*   **Random Entity Expansion:** Using random entities from $D_1$ for the second hop to test if the "bridge" logic is actually filtering correctly.
*   **Single-Hop vs. Multi-Hop:** Comparing the performance gain of the second hop against the added computational cost.

### 9. Failure Modes and Feasibility Risks
*   **KG Sparsity:** If the entities in the documents are not represented in the Knowledge Graph (e.g., very niche or recent topics), the guidance mechanism will fail.
*   **Entity Linking Ambiguity:** Incorrectly mapping a text entity to a KG node (e.g., "Jordan" as a country vs. a person) could lead the second-hop retrieval in the wrong direction.
*   **Latency Overhead:** Multi-pass retrieval combined with KG queries may significantly increase response time, making it less suitable for real-time applications without aggressive caching.
