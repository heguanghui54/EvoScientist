### 1. Title
**Exec-Graph: Execution-Verified Synthesis of Multi-Library Logic via Dependency-Graph Perturbation**

### 2. Problem and Motivation
Current code Large Language Models (LLMs) rely heavily on "The Stack" or similar web-scale repositories, which are dominated by repetitive boilerplate and popular frameworks. Consequently, models struggle with **cross-library reasoning** and **low-resource API usage**. Existing synthesis methods like *Evol-Instruct* or *OSS-Instruct* generate instructions but often produce "hallucinated" code that is syntactically correct but logically flawed. There is a critical need for synthetic data that is both diverse and **execution-verified**, ensuring the model learns functional logic rather than just statistical token patterns.

### 3. Core Hypothesis
Fine-tuning a code LLM on synthetic data generated by perturbing real-world Abstract Syntax Trees (ASTs) and verifying the resulting code via runtime unit tests will improve zero-shot performance on complex, multi-library programming tasks by at least 15% compared to instruction-only synthesis.

### 4. Method
1.  **Seed Extraction:** Sample 10,000 high-quality Python/Rust files from *The Stack v2*. Extract dependency graphs and identify API calls to less common libraries (e.g., specialized scientific computing or obscure CLI tools).
2.  **Graph-to-Requirement Transformation:** Use a teacher model (e.g., GPT-4o) to reverse-engineer a natural language requirement from the code, specifically highlighting the interaction between identified libraries.
3.  **Perturbation & Expansion:** Instruct the teacher model to modify the requirement (e.g., "Change the data source from a local CSV to a streaming S3 bucket") while maintaining the core API constraints.
4.  **Synthesis & Test Generation:** Generate a new code solution and a corresponding set of unit tests (using `pytest` or `unittest`).
5.  **Execution Verification (The Filter):** Run the generated code in a sandboxed Docker environment.
    *   **Success:** If tests pass, add the (Requirement, Code) pair to the training set.
    *   **Failure:** Attempt one round of "Self-Debug" based on the traceback; if it fails again, discard the sample.
6.  **Fine-tuning:** Perform Parameter-Efficient Fine-Tuning (LoRA) on a base model (e.g., CodeLlama-7B or DeepSeek-Coder-Base).

### 5. Dataset or Benchmark
*   **Training Seed:** *The Stack v2* (Python/Rust subsets).
*   **Evaluation Benchmark:**
    *   **HumanEval & MBPP:** For general coding proficiency.
    *   **DS-1000:** For data science-specific library usage.
    *   **CrossCodeEval:** For multi-file/multi-library reasoning.

### 6. Evaluation Metrics
*   **Pass@k (k=1, 10, 100):** Functional correctness on benchmarks.
*   **Library Coverage:** The number of unique, non-standard libraries correctly utilized in the generated outputs.
*   **API Hallucination Rate:** Frequency of the model calling non-existent functions or using incorrect signatures.

### 7. Baselines
*   **Base Models:** DeepSeek-Coder-7B-Base, StarCoder2-7B.
*   **Instruction-Tuned Baselines:** WizardCoder (Evol-Instruct), Magicoder (OSS-Instruct).
*   **Direct SFT:** Fine-tuning on the raw seed data without perturbation or verification.

### 8. Ablations
*   **Verification-Only:** Train on synthetic data without the execution-filtering step to measure the impact of data "noise."
*   **Perturbation-Only:** Train on the reverse-engineered requirements of the original code without modifying the logic.
*   **Teacher Model Scaling:** Compare synthesis quality using GPT-3.5 vs. GPT-4o as the generator.

### 9. Failure Modes and Failure Risks
*   **Environment Setup Overhead:** Automatically configuring environments (installing specific libraries) for 10,000+ different code samples is computationally expensive and may fail for libraries requiring specific hardware (e.g., CUDA).
*   **Triviality Bias:** The teacher model might simplify the "perturbed" requirements to ensure the code passes the tests, leading to a dataset of simple, high-pass-rate code that lacks depth.
*   **Data Contamination:** Risk of the "Seed Extraction" phase inadvertently including snippets already present in the evaluation benchmarks.
