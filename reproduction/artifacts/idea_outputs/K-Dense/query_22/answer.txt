**1. Title**
Adversarial Prefix Optimization for Bypassing Safety Alignment in Code-Generation LLMs

**2. Problem and Motivation**
Large Language Models (LLMs) specialized for code (e.g., StarCoder2, CodeLlama) are increasingly integrated into IDEs and CI/CD pipelines. To prevent the generation of insecure code, providers apply safety alignment (RLHF/DPO) to suppress patterns associated with Common Weakness Enumerations (CWEs). However, existing safety guardrails often rely on shallow lexical triggers. There is a critical need to evaluate whether discrete prompt optimization can discover "universal" adversarial prefixes that force models to ignore safety constraints and prioritize functional completion of insecure patterns, such as SQL injection (CWE-89) or OS command injection (CWE-78).

**3. Core Hypothesis**
A learned adversarial prefix, optimized via gradient-based discrete search (e.g., Greedy Coordinate Gradient), can consistently shift the model's output distribution toward vulnerable code completions by exploiting the tension between "instruction following" and "safety alignment" in the logit space.

**4. Method**
The proposed method utilizes a Gradient-based Discrete Optimization (GDO) approach:
*   **Target Objective:** Maximize the log-likelihood of a "vulnerable suffix" (e.g., a raw string concatenation in a SQL query) given a prompt $P = [A, I]$, where $A$ is the adversarial prefix and $I$ is a benign coding instruction.
*   **Optimization:** Employ a coordinate-wise gradient search to iteratively swap tokens in $A$ that minimize the cross-entropy loss of the target vulnerable sequence.
*   **Constraint:** Maintain a "benign-looking" constraint on the prefix to bypass basic perplexity-based filters.
*   **Inference:** Once optimized on a subset of CWE-specific tasks, test the prefix's transferability across unseen programming languages and different model architectures.

**5. Dataset or Benchmark**
*   **SecurityEval:** A dataset specifically designed for evaluating the security of LLM-generated code across various CWEs.
*   **FormAI:** A large-scale dataset of C code generated by LLMs, used here to extract ground-truth "vulnerable" code patterns for the optimization target.
*   **HumanEval (Security variant):** Modified versions of HumanEval prompts that steer the model toward scenarios where insecure implementations (e.g., using `eval()`) are functionally viable.

**6. Evaluation Metrics**
*   **Vulnerability Rate (VR):** Percentage of generated code snippets containing high-severity vulnerabilities as identified by static analysis tools (CodeQL, Bandit, or Semgrep).
*   **Attack Success Rate (ASR):** The ratio of successful safety bypasses (generating the requested insecure code) to the total number of attempts.
*   **Pass@k:** To ensure the adversarial prefix does not destroy the model's functional coding capability.
*   **Transferability Score:** A measure of how well a prefix optimized for Model A (e.g., Llama-3-8B) performs on Model B (e.g., DeepSeek-Coder).

**7. Baselines**
*   **Vanilla Prompting:** Standard "Write a function to..." prompts without adversarial additions.
*   **Naïve Jailbreaking:** Known human-engineered templates (e.g., "DAN" or "Developer Mode" variants adapted for code).
*   **Few-Shot Insecure Prompting:** Providing $n$ examples of vulnerable code in the context to induce pattern following.

**8. Ablations**
*   **Prefix Length:** Varying the number of tokens in the adversarial prefix (e.g., 5, 10, 20 tokens) to find the minimum effective length.
*   **Target Specificity:** Comparing prefixes optimized for specific CWEs (e.g., only SQLi) versus "Universal" prefixes optimized across a diverse set of vulnerabilities.
*   **Optimization Algorithm:** Comparing GCG (Greedy Coordinate Gradient) against genetic algorithms or random search.

**9. Failure Modes and Feasibility Risks**
*   **Over-Refusal:** The model may become "stubborn" if the safety training is extremely robust, leading to empty or repetitive outputs.
*   **Static Analysis Limitations:** Tools like CodeQL may produce false positives or negatives, potentially misclassifying the "success" of an attack.
*   **Compute Intensity:** Gradient-based optimization on discrete tokens requires significant GPU memory and iterations, which may be a bottleneck for 70B+ parameter models.
*   **Perplexity Filtering:** High-entropy adversarial prefixes might be easily detected by simple input-side perplexity checks.
