### 1. Title
**Confidence-Gated Speculative Decoding with Dynamic Draft Lengths (CG-SDD)**

### 2. Problem and Motivation
Large Language Model (LLM) inference is primarily bottlenecked by memory bandwidth during the autoregressive decoding process, where each token requires a full pass of the model's weights. Speculative decoding mitigates this by using a smaller "draft" model to predict multiple tokens that the "target" model verifies in parallel. However, standard speculative decoding uses a fixed draft length ($k$). This is suboptimal: if the draft model is uncertain, it produces incorrect tokens that are rejected, wasting verification cycles; if it is highly certain, a fixed $k$ might be too short, missing opportunities for further speedup.

### 3. Core Hypothesis
Dynamically adjusting the speculative draft length based on the draft model’s cumulative confidence scores—and terminating the draft sequence early when confidence falls below a learned threshold—will increase effective throughput by reducing the overhead of failed verifications without sacrificing the target model’s output distribution.

### 4. Method
The proposed method, **CG-SDD**, modifies the speculative decoding loop:
1.  **Confidence Estimation:** For each token $t_i$ generated by the draft model $M_d$, we calculate the normalized entropy or the top-1 probability $p_i$.
2.  **Dynamic Termination:** Instead of generating a fixed $k$ tokens, the draft model continues until:
    *   The cumulative confidence (e.g., product of probabilities $\prod p_i$) falls below a threshold $\tau$.
    *   A maximum budget $k_{max}$ is reached.
3.  **Adaptive Thresholding:** The threshold $\tau$ is not static. We implement a "sliding window" controller that adjusts $\tau$ based on the acceptance rate of the previous 10 verification cycles. If the acceptance rate is high, $\tau$ decreases (allowing longer, riskier drafts); if low, $\tau$ increases (forcing shorter, safer drafts).
4.  **Verification:** The target model $M_t$ verifies the draft sequence in a single forward pass. Standard rejection sampling is used to ensure the final output is identical to the target model's standalone distribution.

### 5. Dataset or Benchmark
*   **MT-Bench:** To evaluate multi-turn conversation performance.
*   **GSM8K:** To test the method on reasoning tasks where draft models typically struggle.
*   **HumanEval:** To evaluate performance on highly structured code generation.

### 6. Evaluation Metrics
*   **Token Throughput:** Tokens per second (TPS).
*   **Speedup Factor:** Ratio of TPS (CG-SDD) to TPS (Vanilla Autoregressive).
*   **Acceptance Rate:** Average number of accepted tokens per verification cycle.
*   **Verification Overhead:** Time spent on target model passes that result in zero or one accepted token.

### 7. Baselines
*   **Vanilla Autoregressive Decoding:** No speculation.
*   **Standard Speculative Decoding (Leviathan et al.):** Fixed $k$ (e.g., $k=5$).
*   **Medusa:** Multiple decoding heads without a separate draft model.
*   **Lookahead Decoding:** Parallel decoding without a draft model using Jacobi iterations.

### 8. Ablations
*   **Fixed vs. Adaptive $\tau$:** Compare a static confidence threshold against the sliding window controller.
*   **Confidence Metric:** Compare Top-1 probability vs. Entropy vs. Logit-gap (difference between top 2 logits).
*   **Draft Model Size:** Test with varying draft/target ratios (e.g., Pythia-160M for Llama-7B vs. TinyLlama-1.1B for Llama-70B).

### 9. Failure Modes and Feasibility Risks
*   **Drafting Latency:** If the confidence calculation and threshold logic add significant per-token latency to the draft model, it may negate the gains from reduced verification cycles.
*   **Threshold Oscillation:** The adaptive controller might oscillate between being too conservative and too aggressive, leading to inconsistent throughput.
*   **Hardware Bottlenecks:** On systems with very high compute-to-memory-bandwidth ratios (e.g., small models on H100s), the overhead of managing dynamic lengths in CUDA kernels might outweigh the algorithmic benefits. Implementation will require efficient batching or padding to handle variable-length drafts in a single verification pass.
