This proposal represents the converged output of a multi-agent simulation involving a Principal Investigator, Method Designer, Skeptical Reviewer, and Experiment Engineer.

### 1. Title
**SEM-STRESS: A Deep Evaluation Framework for Code LLMs via Automated Property-Based Testing and Execution Trace Differential Analysis**

### 2. Problem and Motivation
Standard code LLM benchmarks (e.g., HumanEval, MBPP) suffer from three primary flaws:
1.  **Data Leakage/Saturation:** Models are increasingly trained on benchmark data, leading to inflated "memorized" scores.
2.  **Brittle Unit Tests:** Most benchmarks rely on 3–5 static unit tests, which fail to capture edge cases or logical soundness across the entire input space.
3.  **Black-box Verification:** Passing a test case does not guarantee the code follows the correct algorithmic logic (e.g., a model might hard-code a lookup table for known inputs).

There is a critical need for a "deep" evaluation that stressors code logic through diverse input generation and monitors internal execution behavior.

### 3. Core Hypothesis
Evaluating code LLMs using automated Property-Based Testing (PBT) and execution trace comparison will reveal significant logic gaps in models that otherwise achieve high Pass@k scores on static benchmarks. Specifically, semantic robustness (the ability to maintain correctness across thousands of generated edge cases) will provide a more accurate ranking of a model’s reasoning capabilities than simple unit test success.

### 4. Method
The SEM-STRESS framework consists of three modular stages:

1.  **Property-Based Test Generation:** For a given programming prompt, the framework uses a "Teacher" model to define formal properties (invariants) and input strategies (using libraries like `Hypothesis` for Python). Instead of static inputs, it defines ranges, types, and constraints (e.g., "the output list must always be sorted and have the same length as the input").
2.  **Differential Execution Sandbox:** The model-generated code and a verified reference implementation are executed within isolated Docker containers.
3.  **Deep Trace Analysis:** The framework captures the execution trace (variable states at each step). It computes a "Semantic Fidelity Score" by comparing the model’s internal state transitions against the reference implementation to ensure the model isn't just "guessing" the final output via a shortcut.
4.  **Stress Injection:** The framework applies "Input Perturbations" (e.g., extremely large integers, empty sets, Unicode strings) to test the boundaries of the generated logic.

### 5. Dataset or Benchmark
The framework will be applied to **HumanEval-STRESS**, a derivative of HumanEval.
*   **Base:** 164 problems from HumanEval.
*   **Augmentation:** Each problem is augmented with a PBT suite (properties and input generators) and a verified "Gold Standard" implementation for differential analysis.
*   **Languages:** Initial focus on Python and Rust (due to strong type systems and PBT tooling).

### 6. Evaluation Metrics
*   **Pass@PBT:** The percentage of problems where the model passes 1,000+ property-based test cases (a stricter version of Pass@k).
*   **Robustness Gap:** The delta between standard Pass@1 and Pass@PBT. A high gap indicates a model that relies on memorization or brittle logic.
*   **Trace Alignment Score (TAS):** A metric (0.0 to 1.0) measuring the similarity of the model's execution path to the reference implementation.
*   **Failure Diversity:** A count of the distinct types of runtime errors (e.g., RecursionError, Timeout, MemoryError) triggered by the stressor.

### 7. Baselines
*   **Standard Benchmarks:** Traditional Pass@1 and Pass@10 on HumanEval and MBPP.
*   **Current SOTA Models:** GPT-4o, Claude 3.5 Sonnet, and Llama-3-70B-Instruct.
*   **Code-Specific Models:** DeepSeek-Coder-V2 and StarCoder2.

### 8. Ablations
*   **Static vs. Dynamic:** Compare evaluation accuracy using only static analysis (linters/type checkers) versus full PBT execution.
*   **Property Complexity:** Evaluate the impact of using simple properties (output type check) versus complex properties (algorithmic invariants).
*   **Teacher Model Dependency:** Test if properties generated by a weaker model (e.g., Llama-3-8B) are sufficient to catch bugs in a stronger model (e.g., GPT-4o).

### 9. Failure Modes and Failure Risks
*   **Compute Overhead:** Running 1,000+ tests per problem across multiple models is computationally expensive. *Mitigation:* Use early-exit logic (if a model fails the first 10 tests, stop).
*   **Flaky Tests:** Non-deterministic code or environment-specific bugs (e.g., floating-point precision) may cause false negatives. *Mitigation:* Implement a "tolerance" threshold for numerical outputs.
*   **Teacher Bias:** If the Teacher model used to generate PBT properties makes a mistake, the entire evaluation for that problem is invalidated. *Mitigation:* Human-in-the-loop verification for the PBT properties of the benchmark set.
