     Multi-Source Compositional Reasoning via Structured Evidence Routing##
 ProblemLarge language models exhibit impressive single-document reasoning but
   struggle when the answer requires integrating information scattered across
multiple heterogeneous sources — documents, tables, code, images, and structured
     databases. In multi-source settings, models face three interconnected
difficulties: (1) source selection — identifying which sources contain relevant
       evidence among many distractors; (2)evidence alignment — resolving
 cross-document coreference, unit mismatches, and contradictory statements; and
(3) compositional chaining — deriving a conclusion that depends on premises from
different sources in a specific logical order. Existing approaches address these
    sub-problems in isolation: retrieval-augmented generation (RAG) handles
selection but not alignment; tool-use agents handle structured data but flatten
   compositional chains into linear tool call sequences; and chain-of-thought
 prompting improves multi-step reasoning but offers no mechanism for verifying
  that sub-conclusions are correctly grounded in their respective sources. No
     current system jointly optimizes all three sub-problems with a unified
                            architectural mechanism.

HypothesisExplicitly modeling reasoning as routing through typed evidence
channels — where each source type (text, table, code, image) is associated with
a dedicated reasoning operator, and cross-source compositional chains are
represented as a directed acyclic graph of evidence transformations — enables
models to perform multi-source compositional reasoning with higher accuracy and
better source-attribution faithfulness than both monolithic chain-of-thought
prompting and general-purpose tool-use agents.

The key claim is that enforcing a structured evidence graph at inference time
(rather than relying on the model's latent ability to track which conclusion
came from which source) reduces source-confusion errors and improves
compositional chaining accuracy, even when the model itself generates the
evidence graph.

MethodWe propose Structured Evidence Routing (SER), a two-stage inference
framework for multi-source reasoning.

Stage1 — Evidence Graph Construction. Given a query and a set of retrieved
sources (text documents, tables, code snippets, images), the model produces a
directed acyclic graph where:

 • Nodes are evidence statements, each tagged with a source type (text, table,
   code, image) and a source identifier.
 • Edges are typed transformations: extract(k) (pull a value from source),
   convert(t1→t2) (transform between types, e.g., table-to-text), align(id1,
   id2) (resolve cross-source coreference), compose(op1, op2) (chain two
   evidence transformations), and verify(node) (check consistency against a
   source).
 • The graph is constrained to have a single sink node: the final answer.

Stage2 — Constrained Execution. The evidence graph is executed bottom-up by a
set of type-specific resolvers:

 • Text resolver: span extraction + cross-document coreference resolution.
 • Table resolver: programmatic cell lookup + aggregation (e.g., sum, filter,
   join).
 • Code resolver: sandboxed execution of extracted code fragments with test
   assertions.
 • Image resolver: captioning or VQA over relevant image regions.
 • Alignment resolver: cross-source entity linking using a lightweight
   bi-encoder.
 • Composition resolver: applies the dependency order from the graph, enforcing
   that each transformation's inputs are available before execution.

The graph is executed greedily (no backtracking) in topological order. If a
resolver fails (e.g., an extracted table cell is empty), the node is marked as
FAILED and downstream nodes receive a flag — they may attempt recovery via an
alternative path if one exists in the graph, or propagate the failure.

Design rationale. The graph structure is generated by the LLM (no external
planner), keeping the method training-free and compatible with any base model.
The typed resolvers are lightweight (mostly rule-based or small learned
components) and can be implemented with under5K lines of Python. The constraint
that drives performance is separation of concerns: the LLM handles the
high-level reasoning structure (what needs to be extracted, converted, and
composed), while the resolvers handle the concrete operations with guarantees (a
table lookup returns a cell value exactly, a coreference resolver returns the
linked entity ID). This prevents the LLM from hallucinating intermediate values.

Dataset / BenchmarkMulti-Source Compositional QA (MuSiCQA) — we construct this
benchmark from existing datasets, covering four distinct multi-source reasoning
patterns:


 Reasoning Pattern         Source Combination         Construction Source
 Table + Text Composition  Tables with contextual     HybridQA + FeTaQA
                           paragraphs
 Cross-Document Alignment  Multiple text passages     HotpotQA (hard subsets,
                           sharing entities           entity-overlap filter)
 Code + Arithmetic         Code snippets + numeric    TabMWP + math
                           tables                     stackexchange extracts
 Image + Caption           Images with textual        SciQA + A-OKVQA type-2
                           captions                   questions


Each example includes1 query,3–7 sources (2–4 relevant, rest distractors), and a
ground-truth evidence graph annotated by a human. We target1,200 examples (300
per pattern), with a700/250/250 train/val/test split. The test set queries are
designed to require at least3 compositional steps (i.e., the answer depends on
evidence from at least3 different sources, chained in a non-trivial dependency
order).

Additionally, we evaluate on MuSiQue (multi-hop QA with controlled distractor
difficulty) as an out-of-distribution generalization test, and DROP (discrete
reasoning over paragraphs + numbers) to test the text+arithmetic pattern.

Evaluation MetricsPrimary metric. Compositional Accuracy — the final answer must
match the ground truth exactly (for extractive answers) or receive >=0.7 on a
semantic similarity rubric (for abstractive answers) AND every evidence node in
the model's output graph must be traceable to a correct source. This penalizes
correct answers reached via incorrect reasoning.

Secondary metrics.

 • Graph F1: node-level precision/recall of the generated evidence graph against
   the gold graph.
 • Source Attribution Accuracy: for each sub-claim in the reasoning chain, is
   the attributed source correct?
 • Execution Success Rate: fraction of evidence graphs that execute without any
   resolver failure.
 • Hallucination Rate: fraction of evidence nodes whose content is not grounded
   in any provided source.
 • Abstention Rate: fraction of examples where the model declines to answer
   (preferred over hallucinating).
