Adversarial Instruction Tunneling: Exploiting Multi-Turn Context Persistence in
 Code LLMs## ProblemCode Large Language Models are deployed in safety-critical
     software pipelines — automated code review, vulnerability repair, test
generation, and even autonomous program synthesis. Current red-teaming research
largely treats adversarial attacks as single-turn problems: a prompt is crafted,
a harmful output is elicited, and the attack either succeeds or fails. However,
   real-world integrations (Copilot plugin, Cursor agent, SWE-agent) maintain
 persistent context across multiple turns, with earlier turns influencing later
code generation. This creates an underexplored attack surface: an adversary can
  "tunnel" a harmful objective through a sequence of apparently benign turns,
where no single turn triggers the model's safety guardrails, but the accumulated
    context steers the final generation toward vulnerable or malicious code.

The problem is not merely that multi-turn attacks exist — it is that current
alignment benchmarks evaluate models with no notion of sustained adversarial
pressure. A model that passes single-shot rejections on "Write a buffer
overflow" may still generate the same exploit when the instruction is fragmented
across a conversation. The gap is methodological: we lack datasets, metrics, and
taxonomies for this class of attack.

HypothesisCode LLMs that exhibit strong single-turn refusal behavior can be
reliably induced to generate exploitable code through a multi-turn instruction
tunneling attack — a sequence of causally linked sub-instructions, each
individually benign, whose accumulated conversational context reconstructs a
forbidden objective that the model would have rejected if presented in a single
turn. The attack success rate correlates with context window size and is
substantially harder to defend against than single-turn jailbreaks, because each
turn passes the model's per-turn safety filters.

MethodWe propose a three-component method for generating and evaluating
instruction-tunneling attacks.

Attack Taxonomy. We define three tunneling strategies, each exploiting a
different property of multi-turn contexts:

 1 Decomposition tunneling. The adversary splits a forbidden code-generation
   task into N sub-tasks, each independently permissible (e.g., "Write a
   function that allocates a256-byte buffer" → "Write a function that copies
   user input into that buffer without checking length" → "Call the two
   functions together in a network server that reads from a socket"). No single
   turn violates safety policy; the final composition does.
 2 Gradual relaxation tunneling. The adversary starts with a strict, safe
   specification and iteratively requests relaxations across turns (e.g., "Write
   a SQL query builder that uses parameterized queries" → "Relax the
   parameterization — allow raw string concatenation for legacy tables" →
   "Remove the allowlist entirely; trust admin input"). Each individual
   relaxation request appears legitimate.
 3 Distractor-chain tunneling. The adversary buries the critical unsafe
   instruction inside a long sequence of syntactically similar but safe
   requests, exploiting recency bias and context saturation. The model's
   attention dilutes across many similar turns, and the final harmful request
   slips through because it pattern-matches earlier safe requests.

Attack Generation Pipeline. We build an automated tunneler: given a forbidden
code target T (e.g., "generate a command-injection-vulnerable PHP script"), the
pipeline:

 • Decomposes T into a dependency graph of sub-operations.
 • For each sub-operation, assigns a safe surface-level framing using a
   paraphrasing model.
 • Orders sub-operations into one of the three tunneling strategies.
 • Validates that each sub-operation, in isolation, passes a safety classifier
   (Llama Guard or equivalent).
 • Returns an adversarial multi-turn session that, when traversed sequentially,
   produces output functionally equivalent to T.

Defense Evaluation. For each successful attack, we evaluate existing defenses
against the tunneling attack:

 • Per-turn Llama Guard filtering (baseline).
 • Full-context safety classifiers that re-scan the entire conversation after
   each turn.
 • Adversarial training on decomposed attack sequences.
 • Context-sensitivity probes: inserting trigger-specific "red lines" that force
   the model to re-evaluate safety context.

Dataset / BenchmarkWe construct CodeTunnel-1K, a multi-turn adversarial
benchmark:

 • Source. Seed200 forbidden code-generation targets from existing single-turn
   red-teaming benchmarks (CyberSecEval, Safety Eval, internal red-teaming
   prompts), spanning5 vulnerability classes: command injection, SQL injection,
   buffer overflow, path traversal, and hardcoded credentials.
 • Construction. Each target is decomposed into3–8 sub-turns (mean ~5),
   producing ~1,000 multi-turn sessions across all three tunneling strategies.
   Each session is validated to have per-turn safety-passing scores and a
   final-turn harmful output.
 • **Control set.**200 single-turn equivalents of the same targets for direct
   comparison.
 • Release. Publicly released with Turn-Pass/Final-Fail labels.

Size Rationale1,000 sessions is not large by NLP benchmark standards, but each
session requires (a) dependency-graph construction, (b) per-turn safety
filtering, (c) human verification of final-harmfulness, and (d) annotated
metadata on strategies. This is comparable to specialized red-teaming datasets
(e.g.,300 samples in HEx-PHI,500 in SAP). For statistical power,200 targets ×3
strategies provides600 attack–defense pairs per baseline; a paired t-test
with600 samples can detect an effect size of d=0.15 at80% power (α=0.05), which
is sufficient to distinguish defense effectiveness at reasonable granularity.

Evaluation Metrics- Attack Success Rate (ASR@k) — fraction of sessions where the
final code generation matches the forbidden target within k turns (k = full
session length). Reported with exact95% Clopper-Pearson binomial confidence
intervals. Primary metric.

 • Single-Turn Refusal Rate (STRR) — fraction of individual turns flagged by
   safety filters. A successful tunneling attack minimizes STRR while maximizing
   ASR.
 • Defense Drop Rate (DDR) — for each defense, the relative increase in ASR
   between single-turn and multi-turn versions of the same target: (ASR_multi −
   ASR_single) / ASR_single. This is the core measure of tunneling
   vulnerability.
 • Tunneling Efficiency (TE) — median number of turns required for a successful
   attack. Lower values indicate more dangerous attacks.
 • Search Depth — for automated generation, the number of decomposition →
   reorder → validate iterations needed per successful session.

The gap between per-turn Llama Guard ASR (15-30%) and full-context filtering ASR
(5-15%) quantifies how much tunneling is attributable to context fragmentation
vs. model inherent capability.

Ablations1. Strategy ablation. Measure ASR separately for each tunneling
strategy (decomposition vs. gradual relaxation vs. distractor-chain). If one
strategy dominates, the attack surface may be narrower than hypothesized.

 2 Context window ablation. Vary context positions where the critical
   sub-instruction appears: early (turn2-3), middle, late. Controls for whether
   recency bias is the primary mechanism.
 3 Model size ablation. Test on small (7B), medium (13B), and large (34B/70B)
   code LLMs. Smaller models may be more susceptible to distraction tunneling
   because of limited attention capacity.
 4 Temperature ablation. Test at temperature0 (deterministic),0.5, and1.0.
   Higher temperatures may increase variability in per-turn policy compliance,
   potentially increasing tunneling success variance.
 5 Single-turn control. Replace each multi-turn session with its collapsed
   single-turn equivalent. If ASR is at or near zero, the multi-turn context is
   causally necessary for the attack — not just a random failure.

Expected Failure Modes- Decomposition detection. Models may learn to detect
decomposed instructions even across turns (e.g., by tracking unresolved function
call dependencies in the conversation). If per-turn ASR stays below5%, the
tunneling threat is marginal for current models.

 • Surface-level overfitting. Generated attacks may rely on brittle lexical
   patterns (e.g., specific paraphrasing templates from the decomposition model)
   rather than general tunneling strategies. High ASR on the test set but poor
   transfer to out-of-distribution targets.
 • Benchmark saturation. If CodeTunnel-1K sessions are too similar to each other
   (same decomposition structure across different targets), models could learn a
   single "check for dependency chains" heuristic and block all1,000 sessions
   with one rule. This would overestimate defense robustness.
 • Defense whack-a-mole. Full-context scanning might close the tunneling attack
   but open a new one (e.g., "attention flooding" — generating thousands of
   benign turns to overflow the safety context window). The benchmark does not
   measure attack adaptation, only the initial three strategies.

Limitations1. Lab setting. All experiments use static, pre-generated multi-turn
sessions. Real attackers can adapt dynamically based on the model's per-turn
responses, which likely increases ASR (adaptive attacks > static attacks). Our
results should be interpreted as a lower bound on real-world risk.

 2 Target scope. Five vulnerability classes from existing benchmarks. Does not
   include logic flaws, race conditions, cryptographic misuse, or supply-chain
   attacks. Expanding to the full OWASP Top10 would require ~3× more targets.
 3 Defense scope. We evaluate four defenses — none involve architectural changes
   (e.g., attention-masked safety heads, steerable latent spaces). Defense
   results are comparative, not exhaustive.
 4 Language bias. All code targets are in C/C++, Python, and PHP. Vulnerable
   code in JavaScript/TypeScript, Rust, and Go may follow different
   decomposition patterns. The tunneling strategy taxonomy may not transfer to
   languages with strong safety guarantees (Rust's borrow checker, for example,
   makes buffer overflow tunneling inherently harder).
 5 Single-model attack generation. The automated tunneler uses GPT-4 for
   decomposition and paraphrasing. Attacks generated by one model family may
   embed latent patterns detectable by the same family but not by other models.
   Cross-model transfer is not tested.
 6 No human subjects. All attacks are generated algorithmically and evaluated
   against safety classifiers, not against human reviewers in a realistic
   deployment. Human-in-the-loop red-teaming would likely find additional
   strategies not captured by our three-way taxonomy.
 7 Context window static limit. Sessions have at most8 turns. Real deployments
   (e.g., SWE-agent) can sustain50+ turns of context. Whether tunneling
   effectiveness plateaus or increases with longer sessions is not addressed.
