DeCoT: Decompositional Chain-of-Thought with Constraint-aware Schema Linking for
Complex Text-to-SQL## ProblemText-to-SQL remains bottlenecked by complex queries
involving nested subqueries, set operations, multi-joins across many tables, and
domain-specific value constraints. Current approaches fall into two camps, each
                           with a critical weakness:

 • Encoder-decoder models (e.g., T5-based PICARD, RESDSQL) treat schema and
   question jointly but struggle when the schema grows large (10+ tables),
   producing spurious schema links and poor attention allocation.
 • LLM-based prompting methods (e.g., DAIL-SQL, DIN-SQL, C3) decompose the
   problem into schema linking, intermediate reasoning, and SQL generation, yet
   their intermediate representations are typically either full natural language
   chain-of-thought (which is verbose and drifts) or abstract syntax-tree
   sketches (which lose natural-language constraints). Neither is
   constraint-aware — they do not explicitly track foreign-key paths, NOT NULL
   constraints, or type-based filters that determine whether a generated query
   is valid, not just syntactically correct.

The consequence is that on benchmarks like Spider (with its20% multi-table
questions exceeding3 joins) and BIRD (with noisy, real-world database values),
state-of-the-art methods plateau at approximately84–86% execution accuracy.
Gains from scaling model size have largely saturated. The field needs a
structural intervention in how reasoning chains are represented and grounded in
database constraints.

HypothesisReplacing free-form natural language chain-of-thought with a
structured decomposition graph — where each reasoning step is a typed node
(schema link, join path, filter condition, aggregation, nesting) and edges
encode database-level constraints (referential integrity, cardinality, NOT NULL,
domain range) — yields higher execution accuracy on complex Text-to-SQL queries
than either flat NL-CoT or AST-sketch methods, because constraint edges prune
spurious SQL generation paths before decoding.

Method — DeCoTWe propose DeCoT (Decompositional Chain-of-Thought), a two-stage
LLM pipeline operating over a structured decomposition graph.

Stage1: Constraint-aware Decomposition. Given a question and the database
schema, the LLM produces a decomposition graph — not free text, but a structured
JSON containing:

 • Schema-linking nodes: Each maps a question span to a specific table.column,
   annotated with a confidence (hard/likely/ambiguous).
 • Join-path nodes: A sequence of table pairs connected by foreign-key
   relationships, with a flag indicating whether each join is implied or
   explicit in the question.
 • Filter nodes: Predicate triples (column, operator, value) with a type
   constraint field that records the column's domain (e.g., INTEGER >0, DATE <=
   CURRENT_DATE, VARCHAR match prefix). The LLM is instructed to check each
   filter against the column's declared constraints from information_schema.
 • Aggregation nodes: Group-by columns and aggregation functions, with
   constraints on whether the column type supports the aggregation.
 • Nesting nodes: Represent subqueries as their own decomposition sub-graphs,
   preserving the same node types recursively.

The LLM is prompted to fill this structure in a schema-first pass (examining
column types, keys, and nullable flags) and then map natural-language conditions
into filter nodes, rejecting any condition that violates a column constraint. If
no valid mapping exists, the node is marked unresolvable rather than
hallucinated.

Stage2: Constraint-traversing SQL Generation. The decomposition graph is fed
back to the same LLM (or a smaller specialized decoder) with an instruction to
traverse the graph depth-first:

 1 Emit SELECT ... FROM using schema-linking nodes.
 2 Emit JOIN ... ON ... for each join-path node; validate that the join columns
   share compatible types (the constraint edge is pre-checked in Stage1).
 3 Emit WHERE clauses from filter nodes, respecting the pre-validated operators
   and value types.
 4 Emit GROUP BY / HAVING from aggregation nodes.
 5 For nesting nodes, recurse and produce a subquery from that node's sub-graph.

Because constraint checks happen in Stage1, Stage2 is a deterministic traversal
— no backtracking, no self-correction. This eliminates the two failure modes of
NL-CoT: reasoning drift and hallucinated columns.

Training recipe: We use QLoRA fine-tuning of Llama-3-70B on a synthetic dataset
generated by applying DeCoT's decomposition template to existing Spider and BIRD
training splits. The fine-tune objective is a two-part loss: (a) standard
cross-entropy on the decomposition JSON tokens, and (b) a contrastive term that
penalizes constraint-violating decompositions. The contrastive term uses
negatively sampled decompositions where one filter node intentionally violates a
column constraint, and the model must assign lower likelihood to such samples.

Dataset / Benchmark- Spider (train / dev / test): The standard benchmark for
complex cross-domain Text-to-SQL. We report on dev; test via the official
leaderboard. Primary metric: execution accuracy (EX).

 • BIRD (train / dev / test): Real-world dirty database benchmark with noisy
   values. Adds external knowledge for some questions; we do not use external
   knowledge retrieval (to isolate the effect of constraint-aware
   decomposition). Secondary metric: EX on BIRD dev.
 • SParC (cross-context): For evaluating whether the decomposition graph
   degrades across multi-turn contexts. We include a2-turn variant analysis.

Evaluation Metrics- Execution Accuracy (EX) — main metric on both Spider and
BIRD.

 • Exact Set Match (ESM) — structural match without value sensitivity, to
   distinguish SQL structure errors from value errors.
 • Constraint Violation Rate (CVR) — fraction of generated queries that
   reference nonexistent columns, violate type constraints, or produce runtime
   type errors when executed. This is our targeted quality metric.
 • Decomposition Fidelity — human evaluation on200 sampled dev questions: does
   the decomposition graph correctly capture all filters and joins? (measured as
   recall of gold SQL clauses in the decomposition nodes).

Expected Failure Modes1. Schema-dependent decomposition overhead. For questions
against very large schemas (50+ tables), the decomposition graph becomes large
and the model may omit valid join paths. Mitigation: pre-prune schema to the
top-8 tables using a lightweight retrieval model (we will adapt IRNet's schema
pruning to serve as a preprocessing step before Stage1).

 2 Value constraints are incomplete. The information_schema metadata in real
   databases is often missing NOT NULL or CHECK constraints. DeCoT's filter
   validation is only as strong as the available metadata. We will report CVR
   stratified by databases with complete vs. incomplete metadata to characterize
   this gap.
 3 Recursive decomposition for deeply nested queries. The nesting-node
   representation incurs a quadratic token cost for subqueries more than2 levels
   deep, which may exceed the model's context window on long questions. We
   expect this to affect fewer than3% of Spider queries; for those, we fall back
   to flat NL-CoT and flag the fallback.
 4 BIRD external knowledge. DeCoT deliberately does not use external knowledge
   retrieval, so questions requiring domain-specific values (e.g., "teams that
   lost by more than10 points" when "points" is not a column) will fail at the
   filter-node stage. This is by design — we are measuring constraint-awareness,
   not external knowledge.

Limitations1. DeCoT's decomposition graph is a hand-crafted schema of node
types. There may be SQL constructs (pivot, window functions, EXCEPT) that the
graph does not express. Extending the graph to cover full SQL:2003 is future
work.

 2 The method requires fine-tuning on synthetic decomposition data. The
   synthetic data pipeline (applying the decomposition template to existing SQL
   queries) may introduce a distributional bias: the model learns to reconstruct
   decompositions that fit the template rather than any valid decomposition.
 3 DeCoT does not address value ambiguity in the question (e.g., "customers
   from2020" — is2020 a year filter or a string?). Constraint validation catches
   some cases but not all. Ambiguous schema-linking nodes are flagged but not
   resolved within the method.
 4 We evaluate on English-only benchmarks. Cross-lingual Text-to-SQL (e.g.,
   CSpider) may require a language-adaptive extension to the schema-linking
   stage.
