# VeriPlan: Verifier-Gated Replanning for Reliable Multi-Step Agent Reasoning

## 1. Title

**VeriPlan: Verifier-Gated Replanning for Reliable Multi-Step Agent Reasoning**

---

## 2. Problem

Large language model (LLM) agents that interact with external tools (code interpreters, search APIs, file systems) via multi-step reasoning loops have become the dominant paradigm for autonomous task completion (e.g., SWE-agent, AutoGPT, ReAct, CodeAct). However, these systems exhibit a critical failure mode: **error compounding across long horizons**.

When an agent takes an incorrect action at step *t*, subsequent steps build on corrupted state, and the probability of task success decays sharply with trajectory length. Current methods detect failure only after it manifests as an unusable output or a tool error — at which point the agent has already consumed resources and accumulated misleading context. Empirical evidence from SWE-bench shows that state-of-the-art coding agents succeed on ~30-40% of tasks, with the majority of failures traceable to early reasoning errors that were never corrected.

**This proposal tackles the question**: Can we train a lightweight verifier to predict, from the agent's intermediate state (observation + planned next action), whether the current trajectory is on track to succeed, and use that signal to trigger targeted replanning *before* errors compound?

---

## 3. Hypothesis

**Primary hypothesis**: A two-stage agent architecture — (1) structured plan generation with explicit verification checkpoints, followed by (2) verifier-gated replanning using a lightweight binary classifier trained on intermediate agent states — will improve task success rate on multi-step tool-use benchmarks by ≥20% (relative) over end-to-end ReAct-style agents, while adding <15% latency overhead per trajectory.

**Secondary hypotheses**:
- **H2a**: A verifier trained on recoverability (can the agent still succeed from this state?) outperforms one trained on strict correctness (is the last action right?).
- **H2b**: The verifier's signal is most valuable in the first 30-50% of the trajectory, where errors are least visible to the agent itself.
- **H2c**: Fewer than 5,000 annotated intermediate states are sufficient to train an effective verifier (via distilling from a larger model).

---

## 4. Method

### 4.1 Architecture

VeriPlan operates in three phases per task:

**Phase 1 — Structured Plan Generation** (one-shot, no tool calls yet):
Given a task description, the LLM generates a sequence of sub-goals with expected output signatures. Each sub-goal is annotated with a verification checkpoint — a point at which the verifier evaluates the intermediate state. Plan format:

```
Plan: [
  {step: "Read requirements", expected: "list of constraints C1..Ck", checkpoint: true},
  {step: "Query knowledge base for C1", expected: "result R1", checkpoint: true},
  {step: "Compute cache key from R1", expected: "key K1", checkpoint: false},
  ...
]
```

Checkpoints are placed by the LLM at sub-goals where a wrong outcome would propagate (e.g., selecting the wrong API, misinterpreting a specification). The LLM is prompted to label checkpoints.

**Phase 2 — Execute with Verifier Gate**:
The agent executes steps sequentially. At each checkpoint, before the next action begins:
1. Current state = {original task, plan so far, last action + observation, next planned action}
2. The verifier scores this state as `p(on_track | state)` ∈ [0, 1]
3. If `p(on_track) < τ` (threshold, learned from validation data), the agent enters Phase 3

**Phase 3 — Targeted Replanning**:
The agent analyzes the divergence:
- "Here is what I planned: {next sub-goal}. Here is what I observed: {actual}. The verifier flagged this state as off-track. Explain why the mismatch occurred and propose a corrected plan segment."
- The LLM generates a revised plan segment for the remaining steps and execution resumes from Phase 2.

### 4.2 Verifier

The verifier is a binary classifier built from a small LLM backbone (e.g., Llama-3.2-3B or Qwen2.5-7B) with a linear classification head on the final hidden state of the last token. Training data is generated by:
1. Running a baseline ReAct agent on training tasks and logging all intermediate states.
2. Labeling each state with trajectory outcome: `on_track = 1` if the trajectory eventually succeeds, `0` if it eventually fails.
3. Optionally distilling labels from a larger judge LLM (e.g., GPT-4o or Llama-3.1-405B) that annotates each state with a rationale.

**Loss**: Binary cross-entropy. We also experiment with a contrastive variant that pushes on-track and off-track states apart in the representation space.

## 5. Dataset / Benchmark

We evaluate on **two complementary benchmarks**:

| Benchmark | Domain | Avg. Steps | Tasks | Success Metric |
|-----------|--------|------------|-------|----------------|
| **SWE-bench Verified** | Software engineering (patch generation from GitHub issues) | ~8-15 tool calls | 500 | % of resolved issues (applied patch passes tests) |
| **WebArena** (a subset of ≥5-step tasks) | Web navigation and form completion | ~5-10 | ~300 | Task completion rate per site |

Why these two: SWE-bench tests structured reasoning with code (deterministic feedback), while WebArena tests interactive web reasoning (weaker feedback signals). A method that works on both is more likely to generalize.

**Training data for the verifier**: We collect trajectories from a baseline ReAct agent (Llama-3.1-70B) on a held-out training split of SWE-bench (200 tasks, ~2,000 intermediate states after filtering). Labels from trajectory outcome. An additional 500 states are labeled by GPT-4o for the distiller variant.

## 6. Evaluation Metrics

| Metric | Definition | Primary? |
|--------|-----------|----------|
| **Task Success Rate** | % of tasks where agent produces correct final output | Primary |
| **Recovery Rate** | % of off-track states (verifier score < τ) that lead to eventual success | Primary |
| **False Alarm Rate** | % of on-track states incorrectly flagged, causing unnecessary replanning | Secondary |
| **Latency Overhead** | (Avg. VeriPlan wall time − Avg. ReAct wall time) / Avg. ReAct wall time | Secondary |
| **Checkpoint Precision@k** | Precision of top-k highest-uncertainty checkpoints at predicting failure | Analysis |

All primary metrics are reported with 95% confidence intervals over 3 random seeds.

## 7. Baselines

| Baseline | Description | Key Reference |
|----------|-------------|---------------|
| **ReAct** | Standard interleaved reasoning + acting, no replanning | Yao et al., 2023 |
| **Plan-and-Solve** | Decompose task into sub-steps before execution, then execute linearly without replanning | Wang et al., 2023 |
| **Tree-of-Thoughts (ToT)** | Beam search over reasoning steps with self-evaluation at each step | Yao et al., 2023 |
| **Reflexion** | Agent reflects on failures after task completion, retries with accumulated memory | Shinn et al., 2023 |
| **Self-Refine** | Iteratively refine outputs using self-feedback | Madaan et al., 2023 |
| **VeriPlan (ours)** | This work | — |

We also compare against an **oracle** variant: VeriPlan with a perfect verifier (human-annotated on-track states) to establish the upper bound.

## 8. Ablations

1. **Verifier type**: Trajectory-outcome verifier (H2a) vs. distiller verifier vs. per-step correctness verifier.
2. **Verifier backbone size**: 1B → 3B → 7B → 13B parameters. Where does the benefit saturate?
3. **Threshold τ**: Sweep τ ∈ {0.3, 0.5, 0.7, 0.9} on validation set; report test performance for the best.
4. **Checkpoint density**: Every step vs. LLM-selected checkpoints only vs. every *other* step.
5. **No plan, verifier only**: Remove the structured plan; verifier gates on raw ReAct states.
6. **No verifier, plan only**: Structured plan but no verifier feedback; replan only if tool error occurs.

---

## 9. Expected Failure Modes

| Failure Mode | Mitigation Strategy |
|-------------|-------------------|
| **Verifier has low recall** (misses errors) | Train with class weighting and augment with hard negatives from early trajectory states where outcome is uncertain. |
| **Verifier has low precision** (high false alarms) | Treat τ as a tunable hyperparameter; optimize for F0.5 (precision-weighted) on validation data. |
| **Planning overhead negates gains on short tasks** | Model the cost-benefit: only activate the verifier on trajectories predicted to be ≥5 steps (via a length predictor). |
| **LLM ignores the verifier's signal during replanning** | The verifier score is surfaced as a numeric input in the replanning prompt, and the LLM is asked to explain the discrepancy before proposing changes. A hard gate (don't proceed until plan segment is revised) bypasses this issue. |
| **Replanning introduces new errors** | The replanned segment is validated against the original task goal by the verifier again before execution resumes (second-pass gating). |
| **Data efficiency is poor** | Use sequence-level distillation from GPT-4o to generate high-quality training labels; also augment with contrastive pairs (on-track vs. off-track from the same task). |
